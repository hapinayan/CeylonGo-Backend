# Eco-Tourism Phase 01 — Native payment implementation

Branch `feature/eco-native-payment-phase01`, based on verified `develop` at `180998f` (PR #31). This phase delivers offline-tested native checkout and reconciliation code. Online checkout and paid cancellation are disabled by default. No SQL Server, PayHere sandbox, production merchant, or refund execution endpoint was contacted.

## Architecture and API

Native `EcoReservation` / `EcoAvailabilitySlot` and the authoritative shared `BookingReference(module_type='eco_experience')` remain the booking source. Shared `PaymentTransaction`, `PaymentRefund`, PayHere checkout/signature code, schedule locks, history, and notifications are reused. The legacy Activity-backed Eco checkout router remains unmounted, and its IDs are not used as native reservation IDs.

Provider acceptance precedes checkout. A confirmed unpaid reservation defaults to the existing pay-at-location flow until the traveler explicitly starts online checkout. The attempt records the online choice in the shared ledger, and cash confirmation is then disabled for that reservation. Existing cash reservation request payloads remain compatible, except listings with applicable safety requirements now fail closed when their requirements cannot be established. The signed checkout amount/currency come from the authoritative pricing snapshot calculated by native reservation creation. The caller cannot set an amount or payment state. The configured shared CeylonGo merchant is used, with defaults rejected for native checkout. No provider payout is triggered.

| Method and path | Actor and behavior |
|---|---|
| POST `/api/v1/eco-reservations/{booking_id}/payments/initiate` | Owner traveler. Confirmed unpaid held reservation, future slot, currently eligible listing, positive amount, configured merchant and explicit activation. Returns shared checkout response. |
| GET `/api/v1/eco-reservations/{booking_id}/payments/status` | Owner traveler. Returns shared payment status response, including pending, failed, expired, paid or refund lifecycle state. |
| POST `/api/v1/eco-reservations/{booking_id}/payments/cancel` | Owner traveler. Separately gated, policy-eligible paid cancellation and refund request. Unpaid cancellation remains on its existing route. |
| GET `/api/v1/eco-reservations/{booking_id}/payments/refunds` | Owner traveler. Returns amount, currency, ID and decision without exposing Admin identity or gateway identifiers. |
| POST `/api/v1/admin/eco-reservations/refunds/{refund_id}/decision` | Admin. Approve or reject a pending Eco online refund; identical decision replay is harmless. No execution action. |
| POST `/api/v1/payments/payhere/notify` | Reused merchant/signature-verified shared callback. Native dispatch is selected by the canonical reference discriminator. |

## State changes and safeguards

- The SQL Server schedule lock serializes attempts and state changes for an experience. Repeat checkout can reuse the same pending row and immutable order until the earlier of 30 minutes or slot start. Failure closes the attempt. Expiry is shown from the stored timestamp and prevents a second attempt for the same order. An expired or failed checkout does not automatically cancel the reservation or release its hold; the existing eligible unpaid cancellation remains available.
- The shared callback verifies merchant and signature, now using constant-time comparison. Native handling verifies module, owner, amount and currency and uses a gateway capture lock plus schedule lock. The verified capture updates the initial ledger row, reservation and shared reference atomically. A browser return has no effect on status.
- Exact capture replay creates no second write. Late or conflicting successful captures get a ledger record and a pending reconciliation refund without consuming or releasing capacity. A failed event cannot downgrade an applied capture. Notifications and audit records use reservation references and event categories without logging gateway secrets, raw payloads or payment hashes.
- A payment callback authenticates the signed PayHere order, amount, currency and status. The gateway transaction ID is not itself a field in that signature. A distinct ID is routed to reconciliation; Admin must verify gateway evidence before acting on it. Sandbox acceptance must cover this boundary and the durable capture uniqueness guarantees.
- Paid cancellation calculates the eligible full refund from the stored capture, under the reservation's existing free-cancellation cutoff. It releases the hold and creates the pending request in one commit. Outside the free window, cancellation is refused and the capture and hold are retained. Admin approval keeps the refund pending execution; rejection is visible as `refund_rejected` for the initial cancellation request. A rejection does not restore the cancelled slot. No money movement or executed-refund state is fabricated.
- Existing capacity, start cutoff, season/weather restrictions, and mandatory safety acknowledgement remain enforced. The reservation validates optional participant ages against group size and the listing minimum. For flagged permit/guide listings, booking fails closed pending trusted evidence. The per-participant input range is 0–100; a listing-specific maximum and a verified permit/guide workflow are still missing. Existing weather emergency cascade remains Activity-backed.

## Phase 01B implementation and release requirements

The preceding sections describe the Phase 01 baseline. Phase 01B adds the following behavior to the same branch.

- **Refund policy snapshot.** A trusted listing policy supplies the percentage after the existing free-cancellation cutoff. A new reservation snapshots it in the booking transaction. Before the cutoff the refund is 100% of the verified capture. After the cutoff the snapshot allows full, partial, or zero refunds, rounded to currency cents. Zero releases capacity and records the decision without a zero-value gateway item. Earlier bookings and listings without a structured policy retain their existing cutoff behavior.
- **Manual gateway reconciliation.** Admin approval remains separate from execution. `POST /api/v1/admin/eco-reservations/refunds/{refund_id}/reconcile` records processing, reconciliation required, succeeded, or failed after an operator checks the merchant record. The capture reference, amount and currency must match the ledger. Success requires a unique merchant refund reference and a prior processing or reconciliation state. Identical replays return the stored outcome. The capture keeps its captured state for shared duplicate-payment checks, and successful refund accounting uses the existing shared executed state. Traveler refund status omits merchant references. There is no automated submission or external call. [PayHere Refund API](https://support.payhere.lk/api-%26-mobile-sdk/refund-api) documents OAuth, full and partial submissions, and a refund reference. [PayHere Retrieval API](https://support.payhere.lk/api-%26-mobile-sdk/retrieval-api) documents an intermediate refund-processing status. Merchant entitlement and confirmed settlement evidence for this project remain unverified. Operators must check that the merchant refund is actually complete before recording success.
- **Booking safety.** Listing maximum ages are enforced at booking when configured. Permit and mandatory guide checks use trusted, non-revoked records scoped to the exact slot and valid through the slot end. Verification is rechecked during acceptance, checkout, and capture. The records represent slot-wide coverage and cannot substitute for legally required individual permits. Age input is traveler-declared. Neither traveler nor provider booking payloads can set verification flags. Approval, provisioning, and revocation of those records require an operator process.
- **Weather and seasons.** `POST /api/v1/admin/eco-experiences/{experience_id}/restrictions/{restriction_id}/cancel-slots` applies an active restriction to future overlapping native slots. The schedule lock protects closing slots, cancelling held reservations, releasing capacity, and recording notifications in one transaction. Replaying a completed cascade produces zero changes. Captured online bookings require the paid-cancellation gate and queue a full refund for approval. A captured cash booking or an online booking with the gate disabled blocks the transaction for manual intervention. Started slots and the existing Activity-backed emergency route remain outside this operation.

All new tables and native lifecycle status changes remain in the existing unnumbered proposal under `docs/proposals/`. Checkout, paid cancellation, structured policy snapshots, safety records and reconciliation are off by default. Before release, approve the schema, the policy values and their customer-facing disclosure, the clearance provisioning process, finance reconciliation procedures, and isolated SQL Server and PayHere sandbox acceptance. SQL Server transaction-owned locks and actual fund movement are unverified.

## Phase 02 native reviews and financial reporting

Native reservations use booking references with `module_type=eco_experience`. Activity-backed Eco bookings retain their Activity references and numeric IDs. The same numeric ID can exist in both stores.

| API | Phase 02 behavior |
|---|---|
| POST `/api/v1/eco-experiences/{experience_id}/reviews` | Accepts `booking_source=eco_experience` for native bookings. Omitting the source preserves the Activity contract. Native reviews require an owned, completed reservation and its matching shared reference on a public Eco listing. The schedule lock serializes duplicate checks and writes. Public and provider review results include the source. |
| GET `/api/v1/eco-experiences/me/earnings/summary` | Adds provider-owned `native_financials` and separately grouped `provider_settlements_by_currency`. Existing legacy scalar amounts retain their prior definitions. |
| GET `/api/v1/admin/eco-reservations/report` | Admin-only native booking and payment ledger report with stable pagination, provider, booking status, payment status and booking creation date filters. Includes cancellation timestamps, refund lifecycle and reconciliation states, totals across the filtered bookings, and separate settlement totals. |
| GET `/api/v1/admin/eco-experiences/payments/audit` | Adds native monetary totals using the applicable existing filters. The legacy page continues to serve Activity-backed rows. |
| GET `/api/v1/payments/admin/summary` | Adds `native_eco_financials` by currency. Native refunds now appear alongside native captures, outside the legacy commission and refund totals. |

The native report checks shared booking ownership and payment currency and value against the native reservation. It separates applied online capture, unapplied captures requiring reconciliation, cash receipts, pending refunds, executed refunds, and recorded commission. At most one applied online capture and one cash receipt contribute revenue per booking. Case-insensitive repeats of the same capture ID within a booking count once, and refund rows cannot multiply gross capture volume. Settlements belong to the provider ledger, are grouped by currency, and have no native booking allocation. Settlement totals are independent of the booking date filter. Disbursed totals require ledger evidence. No new settlement or payout mutation is enabled.

## Phase 03 sponsorship and native notifications

### Architecture and endpoints

- `POST /api/v1/eco-promotions/me/campaigns/{campaign_id}/payments/initiate` uses an owned, Admin-approved campaign and immutable package price, currency and duration snapshots. Repeated requests reuse the order. The platform PayHere merchant signs checkout using the shared checkout logic.
- The existing `POST /api/v1/payments/payhere/notify` verifies merchant and signature before routing the Eco sponsorship order. A matching successful capture can activate an eligible campaign once and sets its half-open UTC visibility window. Signature, amount or currency rejection leaves the campaign unchanged. A delayed success for an ineligible or cancelled campaign, and a second distinct capture, enter the Admin reconciliation ledger instead of activating or extending the campaign. No payout or refund is triggered here.
- `GET /api/v1/admin/eco-promotions/campaigns/{campaign_id}/payments` lists sanitized ledger records and reconciliation status. `POST /api/v1/admin/eco-promotions/campaigns/{campaign_id}/expire` persists due expiry under the same listing lock. Public list, search and detail stop promoting at the end boundary even before persistence. A new campaign request expires overdue campaigns before checking conflicts. Public visibility still requires an approved published listing and an eligible provider.
- The existing impression/click endpoints can persist a receipt keyed by the signed nonce and event type. Receipt insertion and the daily counter update share a transaction. A native reservation can include `sponsored_tracking_token`. A qualified click for the exact listing can be attributed once to a canonical booking reference, and campaign drill-down analytics exposes the resulting count. Attribution adds no new traveler identity or contact details to tracking responses.
- Native in-app notifications cover reservation requests and booking actions, cash and online confirmations, cancellations, and refund decisions and reconciliation. Provider slot closure notifies affected travelers that existing booking times remain unchanged. The native weather/season cancellation path continues to notify both sides. State transitions, history and notifications commit together. Repeating the same lifecycle transition cannot enqueue a second notification.
- `PATCH /api/v1/provider/eco-experiences/{experience_id}/slots/{slot_id}/schedule` accepts the expected and requested start times. An approved owner can move an open future slot while preserving its duration, holds and prices. The service checks availability, group limits, seasonal rules and any required clearances. Slots with terminal reservations retain their historical schedule. Each committed move records booking history and sends an in-app notice to the affected travelers. Repeating the current target is a no-op, and a stale expected start returns a conflict. Provider payment notices use the booking reference in their title so payments for separate bookings receive separate notices.
- With the ledger enabled, sponsorship visibility also requires a recorded Admin reviewer, and attribution checks both the signed click nonce and the booking reference before adding a row.

### Schema and acceptance

The unnumbered [sponsorship ledger SQL proposal](../proposals/eco_sponsorship_ledger.proposed.sql) requires canonical migrations 020 and 027. It adds capture, event receipt, and attribution tables plus uniqueness for gateway IDs, applied captures, event types per nonce, and attributions. New orders embed the campaign primary key and a random suffix. The callback verifies both the campaign key and exact persisted order value, preserving compatibility with legacy payment reference values. Verify that the addition can be applied transactionally on an authorized isolated SQL Server target and preserve financial records when disabling feature flags or rolling back application code.

Keep `ECO_SPONSORSHIP_LEDGER_ENABLED` and `ECO_SPONSORSHIP_CHECKOUT_ENABLED` off until authorized schema and PayHere sandbox acceptance. The first flag controls new table reads and writes. Keep it enabled for reconciliation of existing issued orders when turning off checkout after release. The pre-existing tracking path uses process-local replay protection until the durable ledger is installed. The durable path deduplicates a signed token and a booking, while fresh tokens across anonymous browsing sessions remain distinct impressions. Approve a retention policy for event receipts and a backfill or archival policy for pre-existing paid campaigns before enabling ledger-backed visibility.

PayHere signs the order, amount, currency and status, and the callback transaction ID requires independent merchant corroboration when two different IDs claim one order. Production acceptance must verify that boundary, exercise concurrent callbacks and tracking events against SQL Server, and define the manual resolution of unmatched or duplicate charges. Expiry persistence is available through Admin and new campaign requests. Campaign reconciliation is manual. Slot schedule changes use the existing native slot, booking history and notification tables.
