It is not an approved numbered migration and is unnecessary for the mounted standalone reservation path introduced by 034. `docs/proposals/gate_2_migration_030_approval_package.md` records the separation. ## Exact checks requiring separate authorization

1. **Read-only identity and ledger check.** Confirm authorized server and database via `DB_NAME()`, `@@SERVERNAME` and machine/instance properties. With a least-privilege account, select version, filename, checksum and execution method from `dbo.schema_migrations`. Compare all rows to the runner's checksums. Specifically check canonical 030, 034, 036 and 040 and the historic 033/034 discrepancy. Use a direct read if ledger presence is uncertain.
2. **Read-only schema inventory.** Query `sys.tables`, `sys.columns`, `sys.types` and `sys.default_constraints` for every table above. Check native slot/reservation nullable flags, timestamps, decimal precision, status defaults, holds/cancellation snapshot, and `users.credential_version`. Check whether Activity slot nullability or the proposed XOR constraint has drifted.
3. **Read-only constraints and shape of existing data.** Inspect `sys.foreign_keys`, `sys.foreign_key_columns`, `sys.check_constraints`, `sys.indexes`, `sys.index_columns` and `sys.indexes.filter_definition` for native and shared keys. Verify trusted module/status predicates, filtered active uniqueness, no duplicate gateway/reference rows, reservation holds matching slot counts, and proper owner/module/reference joins using aggregate counts. Inspect reference/refund/settlement populations by module and status without printing personal data.
4. **Separate disposable SQL Server authorization.** On a specifically approved scratch target, use the exact connected identity guard before every write. Rehearse canonical migration installation/rollback and conditional writes with multiple sessions. Check booking reference/ledger rollback, cash replay, capacity release, deadlocks and bounded retries. A proposed migration must have independent approval. Existing approved integration guards and server allowlists stay unchanged.
5. **Separate payment sandbox authorization.** Verify merchant environment and routing without printing credentials. With outbound sandbox authorization, test initiation, signed callbacks, replay, different charge IDs, amount/currency mismatches, terminal bookings, refunds and payout reconciliation. Do not use production funds or the production database for verification.
