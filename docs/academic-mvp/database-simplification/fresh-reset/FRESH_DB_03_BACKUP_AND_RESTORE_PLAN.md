# Fresh DB 03 ? Backup and recovery plan

**Readiness: pending.** Destination capacity, SQL service-account access, encryption material, verified media and restore time have no live evidence.

1. Owner chooses an access-controlled local volume or dedicated backup share outside application directories and separate from database data files. Proposed name: CeylonGoDB_pre_mvp_<UTC-YYYYMMDDTHHMMSSZ>.bak. Record exact absolute path, UTC timestamp, source server/database identity and operator. Use unique files and preserve previous backups.
2. Estimate source data and log allocations, prior backup sizes where approved, space for full backup plus restore data/log growth, and an agreed safety margin. Measure available bytes on both volumes. Verify SQL Server service-account access and separate operator permissions. Protect the artifact and relevant TDE/backup encryption keys or certificates and restore credentials. Test restore prerequisites before any cutover.
3. With separate backup approval, take a full copy-only backup with checksum and compression if supported. Record media hash, encryption, LSNs, database GUID, app version, and manifest. A backup alone does not prove recoverability. If a preliminary backup precedes the write freeze, take a separately approved final quiesced backup or an eligible documented log chain with matching recovery model and explicit RPO.
4. Under verification approval, validate media header, file list, checksum and RESTORE VERIFYONLY. Separately approve a restore to a new scratch database with independent data/log destinations and no overwrite. Confirm recovery completes, run approved integrity checks, compare migration ledger, catalog and row-count/source manifests, and test account permissions and legacy workflow reads. Measure RTO and record RPO, validation owner and restore evidence.
5. Prove the original remained intact by comparing database identity/state and pre/post catalog and ledger, and by reconciling row estimates or approved exact counts within the same quiesced window. Backup history in msdb changes during an authorized backup. The main application's rows and schema must remain intact prior to the cutover gate.

Preserve the original database under application write freeze during naming cutover, plus a verified backup and restore evidence. Do not rely on reversing destructive DDL. Protect artifacts and backups for the agreed recovery window. No backup, restore, integrity command, or disk measurement was executed in this phase.
