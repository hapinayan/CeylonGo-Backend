# Existing Service Provider Management Backend Audit

**Snapshot:** CeylonGo-Backend, local `develop` at `16ecbc3`, audited 19 November 2026.
**Database baseline supplied for this audit:** `CeylonGoDB`, 88 tables, migrations 001–032 applied.
**Scope:** Provider onboarding, administration and the six provider modules, including related shared services and client contracts.

The audit used the registered FastAPI route objects and OpenAPI, the actual handlers and services, SQLAlchemy mappings, SQL migration source, existing tests, and targeted reads of the adjacent Angular and Flutter source. The master database PDF, historical schema inventory, team guidelines, and `AGENTS.md` informed the baseline. The historical export covers 87 tables and 29 migrations. Migration 030 adds `advertising_payments`, 031 extends attribution, and 032 tightens guide coordinate pairs. The repository exposes 87 mapped application tables, including `users`. `schema_migrations` is tracked outside the ORM and accounts for the 88th table in the supplied baseline. There was no database connection, migration run, application startup, test execution, or client build during this audit.

**Classification:** Implemented means a source-backed runtime workflow exists. Partially implemented means a material lifecycle, integration, or correctness gap remains. Database only means persistence exists without a corresponding service workflow. Not implemented means neither a usable route nor the required feature behavior was found. Blocked means an independent dependency or approval is required. Not applicable means deliberately outside that role or feature. The existence of tests is recorded separately.

## 1. Executive Summary

Provider registration and moderation already work through a shared onboarding flow. An applicant verifies their email by OTP, saves a draft, supplies identity documents, submits for admin review, and sets a password after approval. Approved providers use the same JWT and user store as other roles, with category-specific access controls for management. The most complete operational stack is Homestay. Eco-Tourism is strong in listing, badge and sponsored campaign management. Activities and Rentals support transactional bookings with narrower provider operations. Guides have profile and location review APIs, while Artisan has business, showcase and promotion APIs.

Module 11 should consolidate navigation and provider-facing summaries over existing source modules and fix shared authorization and publication inconsistencies first. The highest-priority findings are a broken Homestay dashboard review field, weaker publication checks on several legacy detail, media and booking routes than on the Interactive Map, and SQL Server query and concurrency gaps. No new provider profile, listing, booking, payment, settlement, review, notification or audit table is needed for the first phase.

## 2. Current Provider Architecture

- `users` is the account and role authority. `provider_profiles.user_id` links the provider business identity to the account. `provider_registration_drafts` stores the staged application by email and `provider_registration_authorizations` stores hashed, purpose-scoped registration tokens. See [provider registration](../../app/routers/provider_registration.py), [provider auth](../../app/routers/provider_auth.py), and [shared dependencies](../../app/core/dependencies.py).
- `get_current_user` decodes the JWT and checks current account activation. `require_approved_provider` adds provider role and profile approval. Module-specific dependencies or handler predicates enforce category and ownership. Homestay additionally supports legacy owner linkage through [homestay permissions](../../app/core/homestay_permissions.py).
- Module routers are registered centrally in [app/main.py](../../app/main.py). Listings remain in module-specific tables. [Map catalog](../../app/services/map_catalog.py) builds a public read model across modules. [Listing sync](../../app/core/listing_sync.py) connects Homestay to shared listing and booking references. Shared financial and engagement schemas exist beyond the currently connected service producers.
- Provider Portal and administrative contracts are interleaved in both provider-prefixed and ordinary module paths. Using route prefixes alone would miss provider-owned Homestay, Eco-Tourism, Artisan, Rental, finance and notifications operations.

## 11. Missing Features and Integration Gaps

1. No unified provider dashboard, account settings, post-approval profile/business edits, or category-scoped workspace contract.
2. No server-side session revocation/logout, account suspension/reinstatement flow, KYC renewal or provider decision audit coverage.
3. Public module visibility conditions can diverge from the map. Admin review and credentials need atomic SQL Server guards and concurrent regression cases.
4. Missing or incomplete provider booking queues and availability outside Homestay/Activities. Guide booking and Artisan reservation storage exist without services. Eco needs a deliberate model for linking booking/availability to its existing slots and references.
5. Shared listing/booking/payment/review/notification services are not uniformly wired. Define canonical writers before exposing cross-module finance or performance totals.
6. No provider payout request lifecycle or cross-module financial reconciliation in this baseline.
7. Angular registration is partially integrated in the inspected checkout. Angular and Flutter operational provider workspaces and end-to-end contract verification remain open.

## 12. Recommended Module 11 Development Scope

Start with a provider account and workspace layer over existing modules. Reuse registration, provider identity, approved-provider dependencies, owned module reads and the notification inbox. Add a shared role/category capability contract and dashboard representation with explicit unavailable modules or metrics. Fix publication filters, onboarding transactional guards, dashboard calculation and provider decision audit before expanding writes. Use existing booking models and shared references for missing read-side provider queues before adding new booking/payment features. Keep payout execution and the attraction catalog deferred unless separately approved.
