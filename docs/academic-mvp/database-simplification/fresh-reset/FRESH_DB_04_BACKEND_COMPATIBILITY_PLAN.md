# Fresh DB 04 ? FastAPI compatibility and separate bootstrap

The existing 99-mapper app cannot be pointed at the proposed 17-table catalog. Introduce an explicit Academic MVP runtime profile, with a dedicated mapper registry/schema contract, profile route composition and startup schema validation. Keep legacy models, handlers and migrations in Git while testing parity and migration of supported clients. Recover by deploying the pinned legacy backend against the retained legacy catalog.

## Bootstrap

Use a reviewed, versioned fresh-schema artifact in a separate migration namespace with its own digest ledger. Creation runs on an explicitly approved empty isolated target with exact-target guard, separate provisioner/runtime principals and no fallback to a different database. Require deterministic schema manifests, approved synthetic fixtures, and database-specific app configuration. Apply FK dependency order and rollback a failed transitional batch only if state and transaction support are verified. Preserve the legacy schema and all migrations 001?043. Historical migrations expect the preexisting users base and cross-module/ledger dependencies including 041?042. Do not replay selective fragments, copy the old ledger, or use ORM create_all against an existing environment.

## Data decision before cutover

Default planning assumption is fresh MVP data and retained legacy history available through a restricted, separately authorized process. Decide which accounts, listings, assets and historical bookings must carry over before execution. If carryover is required, use reviewed copy-only mapping in a separate rehearsed step, preserving identity map, authorization, external asset links and time conversion. Keep unrepresentable financial, legal, audit and evidence records in the protected legacy archive. Reconcile source and target identities, counts, orphan checks and owner access, and obtain privacy and financial approval. Never transfer gateway secrets or raw payment instruments.
