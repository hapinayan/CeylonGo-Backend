# Fresh DB 02 ? Proposed MVP schema

**17 application tables and one bootstrap ledger.** This is a greenfield design that requires FastAPI changes and a separate bootstrap. The 59-table DB-02 profile is the planning minimum for the existing reuse-first implementation, and the exercised legacy profile reached 72. Neither can be replaced simply by pointing the existing application at this design. Count excludes SQL Server internal objects. Native Activity as Adventure, one Admin role, an itinerary generated on demand, and location directions opened through a client map link are assumptions requiring coordinator confirmation.

## Column contract

All tables use dbo. Columns are NOT NULL unless marked nullable with `?`. Unless explicitly permitted, foreign keys use NO ACTION on update and delete. `ID` denotes BIGINT IDENTITY(1,1) PRIMARY KEY. `T` is DATETIME2(3) UTC. `Money` is DECIMAL(12,2), nonnegative. Status keys are VARCHAR and the stated enum membership is enforced by named CHECK constraints. All event and update timestamps are supplied by the service in UTC. ALL other PKs, UQs, FKs and indexes are specified below. FK index recommendations listed here form part of the proposed design. Physical index options require isolated measurement.

Operational table `mvp_schema_versions`: version VARCHAR(20) PK, artifact_name NVARCHAR(255) UNIQUE, sha256 CHAR(64), applied_at T, applied_by NVARCHAR(128). Fresh profiles use a separate artifact namespace; never write fabricated historical versions to the old migration ledger. Dependency creation order is valid as listed except for provider_documents, which follows inventory_units. Named constraints use a consistent table-specific convention.

## Cross-row invariants and proposed contracts

- Profile owner role, identity approval, listing ownership, publication, category and valid geographic coordinates gate discoverability and booking. Approval actions validate the latest current status in a locked transaction. Preserve private evidence access and never log document contents. Vehicle-document and traveler licensing policy is open. If approval requires traveler license evidence in this greenfield profile, design and count explicit evidence storage before sign-off. Do not disable existing checks as a shortcut.
- Bookings start pending. Use half-open time intervals and explicit local-day conversion for nights. Define slot granularity for rentals and guides before schema freeze. Transactionally lock booking/listing and applicable unit keys in stable order, verify approved profile/listing and payment condition, then lock affected slots and sum unreleased quantities, recheck availability, insert all allocations and history, and commit. Booking ID and slot FKs enforce listing consistency. Every capacity mutation, including blackout/availability updates and cancellation, must acquire compatible locks. Homestay party size must fit one selected unit, while its booking allocates one room per night. Bike and guide units are exclusive. Adventure reserves participant quantity in one session. A CHECK constraint alone cannot enforce interval overlap or slot aggregates.
- The payment service serializes state transitions with booking decisions. First selection locks the booking's method. Preserve that method across retries, enforce one active simulated attempt at a time, return a prior result for identical keys, and reject conflicting payload reuse. Simulated success and failure are demo outcomes only. Pay at Location remains unpaid for confirmation. Preserve legacy financial activity separately with its original ledger and reconciliation paths.
- Basic AI itinerary is transient, with a bounded response plus explicit provider-error behavior. Add tables only if durable itinerary history becomes an approved requirement. Map markers use approved listing coordinates. Weather uses the existing adapter and cache. No traveler location history, weather persistence, or payment gateway credentials in this profile.
- Booking actor policy, provider rejection reason, document and photo retention, account migration, and logout token behavior are acceptance decisions. Existing PMT status values and foreign-key layout are not assumed to fit the new contract.
